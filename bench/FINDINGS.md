## 1. Table I is off by ~17x, and blames the wrong variable

**Source:** `a1_refine_scaling.csv` (237 cells, 3 repeats each, all `status=ok`),
`a2_stage_profile.csv` (n=5 per stage), `a2_stage_profile_*.txt` (cProfile)

**Status: numbers refreshed against the current CSVs.** The table below and
everything derived from it was regenerated after `bc09e9d` ("improved
performance", the batched-`merge_components` fix) and the `8994a3c` A1/A2
rerun. The CSV is the source of truth; the previous version of this section
quoted a run that predates that fix and is now stale — every cell in the
triangle ladder is roughly 2x slower than what was previously written here,
consistently across all six rungs, which is itself worth someone's attention
(see the note at the end of this subsection) but does not change which
variable is at fault.

Table I reports ~2.6M triangles refining in **~7 minutes** with smoothing
disabled and the watertightness check skipped. Running exactly that
configuration on a 2.5M-triangle **connected** mesh:

| n triangles | smoothing | watertight check | mean seconds | sd |
|---|---|---|---|---|
| 50,000 | 0 | skipped | 0.18 | 0.01 |
| 250,000 | 0 | skipped | 0.94 | 0.04 |
| 1,000,000 | 0 | skipped | 5.63 | 0.07 |
| 2,500,000 | 0 | skipped | **24.38** | 0.17 |
| 2,500,000 | 15 | checked | 30.09 | 0.17 |

24.4 s, not ~420 s. The reported figure is **~17x** the measured cost for a
connected mesh of that size, and the "substantially slower" default
configuration is only 23% slower (30.09 s vs 24.38 s), not another order of
magnitude.

Cost is mildly superlinear in triangle count, with a fitted exponent of
**1.16-1.31** across both mesh sources and all four configurations — close
enough to linear that triangle count alone cannot produce a 17x surprise.

### The variable that does explain it is component count

At a fixed ~100k triangles, sweeping connected components (smoothing off,
watertight skipped):

| components | mean seconds |
|---|---|
| 1 | 0.33 |
| 10 | 0.56 |
| 50 | 0.92 |
| 100 | 1.12 |
| 250 | 2.18 |
| 500 | 5.42 |
| 1000 | **10.79** |

A 33x increase from component count alone, with the triangle count held
constant. Fitted exponent ~0.48 in component count.

### The two axes are strongly super-additive

| n triangles | components | seconds (smoothing off, watertight skipped) |
|---|---|---|
| 2,500,000 | 1 | 24.38 +/- 0.17 |
| 96,000 | 1000 | 10.79 +/- 0.52 |
| 448,000 | 500 | 14.95 +/- 0.65 |
| 896,000 | 1000 | 48.02 +/- 6.50 |
| 2,496,000 | 1000 | **141.67 +/- 2.67** |

If the axes were additive, 2.5M triangles in 1000 components would cost about
35 s (24.38 + 10.79). It costs 142 s — **~4x** more. Extrapolating one more
step in component count still reaches the reported 7 minutes comfortably, and
a fused pointmap from four 512x384 views can have far more than 1000 islands
after confidence masking.

**Conclusion for §V-C:** the ~7-minute observation is reproducible, but only
as a function of *component count*, not triangle count. The paper currently
presents it as a triangle-count result, which is wrong by more than an order
of magnitude and would mislead anyone sizing a machine for this pipeline.

### Which stage, and which function

`a2_stage_profile.csv`, n=5, also regenerated post-fix. The answer differs by
regime, which is why a single attribution was never going to be right:

| stage | 1M triangles, 1 component | 96k triangles, 1000 components |
|---|---|---|
| `component_filter` | 0.90 s (12.0%) | **9.64 s (95.9%)** |
| `fill_holes` | 0.45 s (6.0%) | 0.03 s (0.3%) |
| `smooth` | 0.96 s (12.7%) | 0.13 s (1.3%) |
| `finalize` | **4.06 s (53.7%)** | 0.16 s (1.6%) |
| `watertight_check` | 1.19 s (15.7%) | 0.10 s (0.9%) |

cProfile, function level — this is the part that changed most since the
merge fix landed:

- **Large connected mesh** (7.87 s total): `finalize_mesh` dominates —
  `clean()` 3.04 s and `compute_normals()` 1.08 s. `split_bodies()` is only
  1.00 s.
- **Many components** (14.23 s total): inside `component_filter`,
  `split_bodies()` now accounts for **10.55 s (74%)** of the *entire* call —
  mostly its internal repeated `threshold()` filter invocations (9.48 s
  cumulative across 1000 calls) — with per-piece `extract_surface` calls
  (1001 of them) at 2.91 s (20%). `merge_components` no longer appears in the
  top 25 functions by cumulative time: the batched-merge fix in `bc09e9d`
  worked, and removed what used to be roughly a third of this regime's cost.

So the previously-suggested fix (batch the per-piece merge instead of looping
`merged.merge(piece)`) has already shipped, and `split_bodies()` — via its
1000 individual `threshold()` calls, one per surviving component — is now the
dominant remaining cost in the many-component regime, not `merge_components`.

**Suggested §V-C revision:** report cost as a function of component count with
the measured exponents, name `split_bodies`'s per-piece `threshold()` calls
and `finalize_mesh` with their measured shares per regime, and drop the
generic "GPU acceleration" future-work item in favour of batching or
vectorizing the per-component extraction in `split_bodies` / `get_component_pieces`.

### Memory

Peak process RSS reached 2.02 GB during the largest cells (down from the
2.51 GB recorded pre-fix, consistent with the batched merge avoiding repeated
full-mesh copies), comfortably inside 16 GB. No cell hit the 240 s budget and
no cell raised `MemoryError`, so the ladder has no ceiling to report on this
machine. Note that `peak_rss_mb` is a process-wide high-water mark and is
monotonic within a run, so it bounds the whole run rather than attributing
memory to one cell.

### Open question: why is every cell ~2x slower than the pre-fix run

The relative story above (component count, not triangle count, and by
roughly the same ~17-33x and ~0.48-1.3 exponents) is unchanged from the
pre-fix numbers. But the *absolute* seconds are consistently ~2.1-2.4x higher
across every triangle-count rung, and ~1.5x higher on the flagship
2.5M-triangle/1000-component interaction cell, than the run this section used
to quote — including on the "1 component" cells, where the batched-merge fix
should be a no-op (a single-piece `.merge([])` call vs. the old
`.copy(deep=True)`). That gap has not been root-caused here: it could be
machine variance between the two runs (single laptop, no isolation), or a
real cost difference in `pieces[0].merge(list(pieces[1:]), merge_points=False)`
vs. `pieces[0].copy(deep=True)` for the single-piece path. Worth a rerun with
the machine otherwise idle before this table is cited again.

|---|---|---|---|---|

**This must be reconciled before publication.** Either:
- (a) change the code to keep the largest component by `n_cells` in object
  mode, which makes §V-B true but breaks that existing test and changes
  behaviour for multi-sheet captures; or
- (b) change §IV-D/§V-B/Fig. 3 to say component filtering is a *room*-mode
  operation, and that object mode deliberately preserves all components.

This has been reconciled: see the fixed-behaviour note above.

## 3. The hole-fill guard is inverted with respect to what you would want

**Status: fixed.** `fill_mesh_holes` now takes an explicit `guard_mesh`
argument and `clean_mesh` passes it the raw, pre-component-filter mesh, so
`is_sheet_like` is evaluated against the actual capture rather than against
whatever component filtering happened to leave behind. A real MASt3R
pointmap is fragmented into many islands by confidence masking (finding 1),
so on production input this reliably reads as non-sheet-like and hole
filling proceeds; the single-piece synthetic `pointmap_sheet` fixture used
below still reads as sheet-like on its own, which is correct — a mesh that
really is thin and open both before and after filtering should still skip.
`tests/test_bench.py::test_hole_filling_is_skipped_on_a_sheet_like_raw_input`
and `test_hole_filling_uses_the_raw_mesh_for_the_guard_not_the_filtered_one`
pin the fixed behaviour. Regenerated against the fixed code:

| base | mode | guard fires |
|---|---|---|
| icosphere | either | 0% |
| torus | either | 0% |
| pointmap_sheet | either | **33%** (exactly the `n_fragments_injected=0` rows) |

The guard now depends only on the raw input, so object and room mode agree
exactly (they see the same raw mesh before filtering diverges them) — the
mode-dependent split in the pre-fix table below is gone. It fires only when
the sheet has zero injected fragments; with any debris present (5 or 20
fragments, the more realistic case, since a real pointmap is fragmented by
confidence masking per finding 1) the raw input is already non-sheet-like and
filling proceeds. The rows and prose below this point are the pre-fix
measurement, kept for the record.

**Source:** `a3_refine_quality.csv`, column `holefill_guard_fires`

`fill_mesh_holes` returns early when `hole_size is None and
is_sheet_like(mesh)`, where sheet-like means min/max bounding span < 0.15. The
guard is evaluated on the *component-filtered* mesh, not the raw input, and
that turns out to matter:

| base | mode | fragments injected | guard fires |
|---|---|---|---|
| icosphere / torus | either | any | 0% |
| pointmap_sheet | object | 0 | **100%** |
| pointmap_sheet | object | 5 or 20 | **0%** |
| pointmap_sheet | room | any | **100%** |

On a clean sheet-like mesh — which is what a fused per-view pointmap is — the
guard fires and hole filling never runs. Adding scattered debris *disables*
the guard in object mode, because `keep_object_components` merges the
fragments in and their spread fattens the bounding box out of the sheet-like
regime. Room mode drops the fragments first, so it stays sheet-like and the
guard fires regardless.

So in the default configuration hole filling was skipped exactly on the clean
reconstruction output it is meant to repair, and ran only when debris happened
to widen the bounding box. §V-B described a code path that did not execute on
the pipeline's own inputs. Now fixed by moving the guard to the raw input, per
the note above.

## 4. Smoothing: Taubin shrinks less than Laplacian, but not by as much as claimed

**Source:** `a3_refine_quality.csv`, `part=smoothing_baseline`,
column `volume_ratio_vs_clean` (324 rows)

Volume relative to the clean original. Only the watertight bases have a
defined volume; the sheet is open and is reported as such rather than being
given trimesh's signed-volume estimate for an open surface.

| base | iterations | Taubin | Laplacian | no smoothing |
|---|---|---|---|---|
| icosphere | 15 | 0.99979 | 0.99942 | 0.99973 |
| icosphere | 50 | 0.99983 | 0.99868 | 0.99973 |
| icosphere | 100 | 0.99984 | 0.99759 | 0.99973 |
| torus | 15 | 0.99950 | 0.99895 | 1.00015 |
| torus | 50 | 0.99737 | 0.99607 | 1.00015 |
| torus | 100 | 0.99714 | 0.99200 | 1.00015 |
| pointmap_sheet | any | n/a (open) | n/a (open) | n/a (open) |

The direction of the claim holds — Laplacian shrinkage compounds with
iteration count and Taubin's does not, on the sphere — but it is
**shape-dependent**. On the torus Taubin loses 0.29% of volume by 100
iterations against Laplacian's 0.80%: better by 2.8x, not the "shrink-free"
that §V-B implies. On the sphere Taubin is effectively flat (0.016% vs 0.24%).

At the shipped 15 iterations both are within 0.1% of the original on every
shape, so the choice is defensible but its practical effect at default
settings is small. Say that rather than implying it is dramatic.

Chamfer is consistently *lower* for Taubin than Laplacian at matched
iterations (e.g. torus at 100: 0.00188 vs 0.00219), so the choice is
supported on accuracy as well as volume.

is gone. Regenerated against the fixed code (mean over holes, fragments and
seeds):

|---|---|---|---|---|---|---|
| icosphere | object | 0.000 | 0.00504 | 0.00162 | -0.00342 | 0.93 |
| icosphere | object | 0.010 | 0.00596 | 0.00380 | **-0.00216** | 1.00 |
| icosphere | room | 0.000 | 0.00504 | 0.00162 | -0.00342 | 0.93 |
| icosphere | room | 0.010 | 0.00596 | 0.00503 | -0.00093 | 0.81 |

| pointmap_sheet | room | 0.010 | 0.00590 | 0.00464 | -0.00126 | 0.89 |

**Both modes now improve Chamfer at every sigma on every base**, and object
mode improves it *more* than room mode everywhere noise is injected (e.g.
icosphere at sigma=0.01: object -0.00216 vs room -0.00093). Normal

| base | mode | before | after |
|---|---|---|---|
| icosphere | object | 0.7870 | **0.9475** |

| torus | object | 0.7712 | **0.9268** |

Object mode's normal-consistency advantage is unchanged from the pre-fix
measurement (still driven by plain `smooth_taubin` vs room mode's
feature-preserving variant, per the original analysis below) -- but it no
longer costs anything on Chamfer. **Object mode now dominates room mode on
both axes**, for the simple reason that discarding injected debris helps
geometric accuracy in every mode, and object mode's smoothing was already
better for surface consistency. §V-B's four assertions should become:
component filtering removes fragments in both modes (finding 2); hole
filling mostly proceeds, being skipped only for the rare zero-fragment case
(finding 3); Taubin smoothing improves normal consistency substantially in
object mode and marginally in room mode; and refinement's effect on
geometric accuracy is now positive in both modes, and larger in object mode.

The material below is the pre-fix measurement and analysis, kept for the
record -- the "opposite trade-off" conclusion it reaches no longer holds.

**Source:** `a3_refine_quality.csv`, `before_chamfer_l1` vs `after_chamfer_l1`

This is the result that most changes how §V-B should be worded. Chamfer to the
clean original, before and after refinement (mean over holes, fragments and
seeds):

| base | mode | sigma | before | after | delta | fraction improved |
|---|---|---|---|---|---|---|
| icosphere | object | 0.000 | 0.00485 | 0.00495 | +0.00010 | 0.70 |
| icosphere | object | 0.010 | 0.00594 | 0.00667 | **+0.00074** | 0.48 |
| icosphere | room | 0.000 | 0.00485 | 0.00152 | **-0.00333** | 0.81 |
| icosphere | room | 0.010 | 0.00594 | 0.00503 | -0.00091 | 0.89 |
| torus | object | 0.010 | 0.00587 | 0.00693 | **+0.00106** | 0.44 |
| torus | room | 0.010 | 0.00587 | 0.00492 | -0.00096 | 1.00 |
| pointmap_sheet | object | 0.010 | 0.00587 | 0.00881 | **+0.00293** | 0.33 |
| pointmap_sheet | room | 0.000 | 0.00945 | 0.00112 | **-0.00833** | 0.67 |

**Object mode makes Chamfer worse** at every noise level above 0.002, on every
base — it retains the fragments (finding 2), and those fragments are pure
error against the clean original. **Room mode improves Chamfer substantially**,
and almost all of that improvement is fragment removal rather than smoothing.

Normal consistency moves the opposite way:

| base | mode | before | after |
|---|---|---|---|
| icosphere | object | 0.7875 | **0.9327** |
| icosphere | room | 0.7875 | 0.8029 |
| torus | object | 0.7710 | **0.9110** |
| torus | room | 0.7710 | 0.7819 |
| pointmap_sheet | object | 0.7325 | **0.8739** |
| pointmap_sheet | room | 0.7325 | 0.7479 |

Object mode improves normal consistency by ~0.15; room mode barely moves it
(~0.02). The cause is in `smooth_mesh`: object mode runs plain
`smooth_taubin`, while room mode adds `feature_smoothing=True,
feature_angle=45`, which deliberately preserves sharp features — and injected
surface noise reads as features, so it survives.

So the two modes trade off in opposite directions, and neither dominates:

- **object mode**: better surfaces (normal consistency +0.15), worse geometry
  (Chamfer +0.0007 to +0.003, because fragments are kept)
- **room mode**: better geometry (Chamfer -0.001 to -0.008, from fragment
  removal), barely-improved surfaces (feature-preserving smoothing keeps the
  noise)

Boundary edges fall in both modes (icosphere 128 -> 26, sheet 506 -> 268 in
object mode) but the output is watertight in only 0-50% of cells, so the
non-watertight warning is doing real work rather than being defensive.

§V-B's four assertions should become: component filtering removes fragments
*in room mode only*; hole filling is usually skipped (finding 3); Taubin
smoothing improves normal consistency substantially in object mode and
marginally in room mode; and refinement's effect on geometric accuracy is
*negative* in object mode. That is a more useful and more defensible claim
than the current uniform "refinement improves everything".

## 5. Frame selection and pairing are working against each other (§IV-C)

**Source:** `a5_frame_budget.csv`

`_cap_frames` sorts by `(motion_score, index)` descending and returns the top
40 **without re-sorting by index**. Above the budget, `job.image_uris` are in
motion-rank order. `dust3r`'s `swin` scene graph — the default for video
sequences, i.e. exactly the case that overflows the budget — pairs purely by
list adjacency.

Measured over three motion schedules (50, 64 and 80 sampled frames against a
40-frame budget):

| pairing | variant | Kendall tau | median pair gap | p95 gap | pairs >1 s apart |
|---|---|---|---|---|---|
| swin | V1 as-implemented | -0.042 | 184.5 | 542.3 | 0.894 |
| swin | V2 motion + re-sort | +1.000 | 27.8 | 174.7 | 0.478 |
| swin | V3 uniform | +1.000 | 41.3 | 436.8 | 0.718 |
| complete | V1 as-implemented | -0.042 | 229.2 | 533.9 | 0.917 |
| complete | V2 motion + re-sort | +1.000 | 229.2 | 533.9 | 0.917 |
| complete | V3 uniform | +1.000 | 215.8 | 539.3 | 0.946 |

Gaps are in source frame indices. The `complete` rows are the control: that
strategy is order-independent, and V1 and V2 are identical there to the
digit. The effect is specifically the interaction between motion-rank ordering
and adjacency-based pairing.

Re-sorting into capture order (V2) reduces the median pair gap by 6.6x and
roughly halves the fraction of pairs more than one second apart, at zero cost:
the same frames, in a different order. V2 also beats uniform subsampling (V3)
on adjacency, because motion-concentrated frames are closer together in time
than an even spread across the whole clip.

**This is an integration failure mode invisible to anyone benchmarking the
reconstruction network in isolation, which is precisely the paper's thesis.**
Whether it changes reconstruction quality is B4's job; the ordering defect
itself is established here without a GPU.

§IV-C's current wording ("frames are ordered deterministically by source,
index, and identifier, and the job is capped...") describes the pre-cap
ordering and does not mention that the cap discards it.

## 6. Multi-camera sync recovery is accurate and robust (§IV-A)

**Source:** `a6_sync_offset.csv`, 4455 trials

Across injected offsets of 0 to ±640 ms, timestamp jitter sigma in {0, 5, 20} ms,
2-4 sources, `tolerance_ms` in {60, 120, 240} and per-camera motion-score noise
in {0, 0.01, 0.05}:

- mean absolute offset-recovery error **2.14 ms** overall
- sign recovered correctly in **100%** of trials
- group-formation rate **0.998**, at every tolerance tested
- no breakdown point inside the tested range

Error by injected offset magnitude:

| \|offset\| (ms) | 0 | 40 | 80 | 160 | 320 | 640 |
|---|---|---|---|---|---|---|
| mean \|error\| (ms) | 1.16 | 2.91 | 1.23 | 2.92 | 1.23 | 2.91 |

The error does not grow with offset magnitude; it alternates between two
values depending on whether the offset is a multiple of the sample grid.

Recovery is insensitive to motion-score noise even at 0.05, which exceeds
`MOTION_MATCH_TOLERANCE` (0.03). That is a genuine property of the algorithm:
`_best_motion_signature_offset` buckets all within-tolerance candidate offsets
by `OFFSET_BUCKET_MS` and takes the median of the most populated bucket, so
spurious matches spread across buckets while true matches concentrate.

The residual 1.2-2.9 ms error is `OFFSET_BUCKET_MS = 100` quantisation
interacting with the sample grid, not a function of the offset magnitude.
`MIN_MOTION_VARIANCE` never fired: the guard triggered in 0% of trials, so
that constant is untested by this experiment and should not be claimed as
validated.

**Caveat to state honestly:** derived streams are time-shifted copies of one
motion sequence with per-camera score noise, not genuinely distinct
viewpoints. This measures clock-offset recovery given a shared motion event;
it does not establish robustness to cameras that see the same event with
different motion magnitudes.

Given no breakdown inside ±640 ms, `tolerance_ms=120` is not doing much work
and could be justified — or relaxed — from this data rather than by intuition.

## 11. B7: reproducibility holds bit-for-bit on GPU, whether or not it is requested (§V-D)

**Source:** `b7_determinism.csv`, 3 scenes (`scan24`, `scan37`, `scan40`) x 2
`deterministic_requested` settings x 2 repeats, `device=cuda` (Tesla T4),
`seed=0`, `cache_cleared=True` on every row, warm-up run discarded before the
measured sweep.

Across all 6 rows, with no exceptions:

| metric | value |
|---|---|
| `hausdorff95_between_runs` | **0.0** |
| `chamfer_between_runs` | **0.0** |
| `point_count_delta` | **0** (300,000 vs 300,000) |
| `glb_byte_identical` (SHA-256 of the exported mesh) | **True** |

This holds for `deterministic_requested=True` **and** `deterministic_requested=False`.
`deterministic_recorded` mirrors `deterministic_requested` exactly in every row
(manifest bookkeeping is correct), but the two repeats are bit-identical
regardless of which value was requested. §V-D's claim -- "supporting
reproducible re-execution of a given job" -- is true for this GPU, these three
scenes, and this seed: not because the determinism flag forces it, but because
CUDA's default kernel selection for this workload's ops already lands on the
same result twice.

`deterministic_applied` is **not** evidence of anything here: `_set_determinism`
returns `True` whenever `torch.use_deterministic_algorithms(...)` doesn't raise,
regardless of which boolean was passed, so it reads `True` for both requested
settings. `deterministic_recorded` (from the run manifest) is the column that
actually reflects what ran.

### The flag is not free

`deterministic_requested=True` costs a consistent ~20 s per run, regardless of
scene size:

| scene | mean wall (det=True) | mean wall (det=False) | delta | glb size (det=True) |
|---|---|---|---|---|
| scan24 | 114.35 s | 94.65 s | +19.70 s (+20.8%) | 37.0 MB |
| scan37 | 109.23 s | 89.16 s | +20.07 s (+22.5%) | 14.4 MB |
| scan40 | 118.56 s | 98.18 s | +20.38 s (+20.8%) | 36.5 MB |

The overhead is ~20 s / ~21% on every scene despite scan37's output being 2.5x
smaller than scan24/scan40's -- consistent with a fixed per-run cost (disabling
CUDA's algorithm auto-tuning) rather than one that scales with mesh or point
count. Separately, `deterministic_requested` changes the *output*: GLB byte
counts differ between True and False for the same scene (e.g. scan24:
37,045,968 vs 37,033,920 bytes) even though the subsampled point cloud is
capped at the same 300,000 points either way -- the two settings are not
interchangeable, only self-consistent across repeats.

**Suggested §V-D addition:** state the measured bound -- zero Hausdorff-95 and
Chamfer divergence, byte-identical GLBs, across 3 scenes x 2 repeats on a
Tesla T4 -- and note the ~20 s / ~21% wall-clock cost of requesting
`torch.use_deterministic_algorithms(True)`, which bought no additional
measured reproducibility on this hardware for this workload.

**Caveats to state honestly:** n=3 scenes, one seed, one GPU model
(Tesla T4), `device=cuda` only -- the module supports a CPU/GPU cross-device
sweep and none ran here, so this says nothing about cross-device or
cross-GPU-architecture reproducibility, only same-device repeat-run
reproducibility. A result this clean (exactly 0.0 to 9 decimal places, every
row) is also exactly what a broken comparison would produce, so before citing
it: `bench/exp_b7_determinism.py`'s own docstring documents two specific
failure modes (cache reuse, index-order artifacts) it was written to avoid --
`cache_cleared=True` and non-trivial `point_count_delta`/`glb_bytes` variation
*between* determinism settings on the same scene both corroborate that those
guards held, but a wider seed/scene sweep would make the zero more convincing
than three scenes can.

## Smaller items from the protocol's checklist

- `compute_priority_score` is computed by `LatencyAwareResourceTagger`, stored
  on the schema and copied into `ReconstructionJob.metadata`, but **no code
  reads it** to change scheduling or any other behaviour. Describe it as
  recorded-but-unconsumed in §VII.
- `_patch_tsdf_cuda_hardcode` replaces `torch.Tensor.cuda` **process-wide**,
  not just for the TSDF optimiser. It is guarded to CPU-only builds and is
  idempotent, but it is a global side effect and belongs in §VII. B5 records
  whether it was applied on every row.
- Refinement's stage timings and output-side counters now land in
  `refinement_manifest.json` and `run_manifest.json` automatically, so §V-D's
  reproducibility claim has machine-readable backing rather than a description.
