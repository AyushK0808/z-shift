# Paper

IEEE conference paper for z-shift.

## Layout

```text
paper.tex                       the paper (IEEEtran, conference mode)
diagrams/*.mmd                  Mermaid source for the single architecture figure
figures/*.png                   rendered figures, referenced by paper.tex
outputs/                        hand-captured source images (not regenerated)
render-diagrams.sh              regenerates figures/fig1-overview from diagrams/
compose-case-study-figure.py    regenerates figures/fig6 (input photo + render)
trim-refine-scaling-figure.py   regenerates figures/fig9 (2-panel) from bench/results/
trim-refine-quality-figure.py   regenerates figures/fig12 (2x2) from bench/results/
mermaid-config.json             Mermaid theme (serif, print-friendly greys)
puppeteer-config.json           browser path used by mermaid-cli
```

`figures/fig6-case-study-validation.png` is composed from two source images in
`outputs/` -- `teddy.jpeg` (one of the case study's eight input photographs)
and `blender-output.png` (a Blender render of the traced case study's refined
mesh) -- placed side by side (a | b) by `compose-case-study-figure.py` at
exactly `\columnwidth`. Neither source image is generated; replace
them by hand if the case study changes, then rerun the script.

`figures/fig7-stage-timings.png` and `figures/fig8-mesh-reduction.png` are
copied in from `bench/results/`, generated by
`bench/generate_case_study_plots.py` from the same case-study numbers printed
in Table II of `paper.tex` -- they are a visual cross-check on that table, not
an independent measurement, so re-run that script and re-copy if the case
study is ever re-run.

`figures/fig9-refine-scaling.png` is generated by this directory's own
`trim-refine-scaling-figure.py` from `bench/results/a1_refine_scaling.csv`
directly -- it is a paper-specific 2-panel derivative (component count; both
axes together) of the 3-panel `bench/plots.py` figure of the same underlying
data, dropping the triangle-count-alone panel because Fig.~9(b) already
contains that curve. **Do not** copy `bench/figures/fig4_refine_scaling.png`
over it -- that reintroduces the 3-panel version and silently undoes this.
`figures/fig11-rigging-quality.png` is copied in from `bench/figures/` (see
"Benchmark-suite figures" below) but is not currently referenced by
`paper.tex`; `fig10-fragment-removal.png` was dropped from the paper (Table
III already reports the same finding) and is no longer used.

## Building the PDF

`IEEEtran.cls` is not vendored here. Either compile on Overleaf (it ships
IEEEtran), or install a TeX distribution locally and run:

```bash
pdflatex paper.tex && pdflatex paper.tex   # twice, to resolve \ref and \eqref
```

The second pass is required — figure and equation cross-references come out as
`??` after a single run.

## Regenerating the figures

The figures are generated, not hand-drawn. Edit the `.mmd` source, then:

```bash
./render-diagrams.sh
```

This needs Node.js (for `npx`) and a local Chrome. If Chrome is somewhere other
than the default Windows path, update `executablePath` in
`puppeteer-config.json` — use forward slashes.

The paper carries a single architecture diagram, `fig1-overview`, rather than
one figure per stage. Earlier drafts split media ingestion, multi-view
reconstruction, and mesh refinement/delivery into three additional diagrams,
but four figures cost roughly a full column of vertical space once captions
are counted, which does not fit a six-page target; the four were merged into
one `flowchart TB` covering ingestion through the TSDF-fusion decision,
refinement, and outcomes routing, with each stage collapsed to a short
multi-line node label rather than exploded into its own diagram. It is
single-column (`figure` at a fraction of `\columnwidth`) and deliberately runs
long instead of wide, since a tall narrow diagram survives a two-column layout
far better than a wide one squeezed down to column width; `rankSpacing`/
`nodeSpacing` are tightened in the file's front-matter to keep the merged
12-node flow's printed height manageable at a single-column width. Rendered at
roughly 580-660 dpi. The paper references exactly four figures -- fig1, fig6,
fig9, and fig12 -- and every one is single-column, so nothing spans the full
text width:

| figure | covers | printed height @ its placed width |
|---|---|---|
| fig1-overview | full architecture: ingestion, job construction, MASt3R alignment, TSDF fusion or point-map fallback, refinement, outcomes routing | 5.5 in @ 0.6 columnwidth |
| fig6-case-study-validation | input photo + render, composed (not a screenshot), side by side a \| b | 1.2 in |
| fig9-refine-scaling | component count vs.\ cost, and both axes together, side by side a \| b | 1.6 in |
| fig12-refine-quality | Chamfer, normal consistency, Taubin-vs-Laplacian volume, 2x2 with the shared legend in the fourth cell | 2.8 in |

The three plot/photo figures were laid out flat (rows and a 2x2, not vertical
stacks) and re-rendered at `figsize == \columnwidth`; together that cut ~8.7 in
of column height, close to a full column, when the paper was one column over
its six-page target. Two rules came out of that and are worth keeping:

- **Render at the width the figure is placed at.** A figure rendered 7 in wide
  and placed in a 3.5 in column has every font halved on the way onto the page
  -- a 6.5 pt tick label arrives at ~3.2 pt. The point sizes in the scripts are
  only honest if `figsize[0]` equals the placed width.
- **Prefer flat layouts to tall ones.** Panels stacked vertically at column
  width cost roughly (panels x width / aspect) inches; the same panels in a row
  or a 2x2 cost a fraction of that. `height=...\textheight` caps bound the
  damage but do not fix it, and they silently shrink the figure's width too.

`fig1-overview` is now over half the paper's total figure height. It is a tall
`flowchart TB`, so the lever there is a wider Mermaid layout rather than a
smaller `\includegraphics` width -- at 0.6 columnwidth its node labels are
already small.

If you rewrite a diagram, check its printed height doesn't run past a column
(roughly 9 in usable on a letter page): render it, then compare `width/height`
against `\columnwidth` (3.5 in) or `\textwidth` (7.16 in) as appropriate.
`rankSpacing`/`nodeSpacing` in the per-file front-matter trims height if a
diagram is too tall.

Colour is applied with `classDef` per stage — blue for ingestion, amber for the
schema artifact, violet for reconstruction, teal for refinement, orange for
deliverables, red for rejection paths. There is no rigging colour: automatic
rigging is future work (see the paper's Future Work section), not part of the
current architecture, so it does not appear in any diagram. Keep colour
assignments consistent across figures — the same stage should be the same
colour everywhere it appears.

## Benchmark-suite figures (fig7-9)

`fig9-refine-scaling.png` is generated from the committed CSV by this
directory's own `trim-refine-scaling-figure.py` (`python
trim-refine-scaling-figure.py`, requires only matplotlib), reading
`../bench/results/a1_refine_scaling.csv` directly -- it does **not** copy
from `bench/figures/`. It reproduces the component-count and
both-axes-together panels of `bench/plots.py`'s `fig4_refine_scaling` (which
stays 3-panel for its own, non-paper purposes) but drops the
triangle-count-alone panel, since Table I was cut from the paper (that
finding is already visible via the "1 component" curve in panel (b)); if you
regenerate `bench/plots.py`'s figures after a code change, re-run
`trim-refine-scaling-figure.py` too rather than copying its output over
`fig9-refine-scaling.png`.

`fig12-refine-quality.png` works the same way, via this directory's own
`trim-refine-quality-figure.py`, reading
`../bench/results/a3_refine_quality.csv` directly. It plots the same three
panels as `bench/plots.py`'s `fig5_refine_quality` (which stays 1x3 and wide
for its own purposes) but arranges them 2x2, with the six-series legend that
panels (a) and (b) share moved into the fourth cell so it does not sit on top
of the data in two ~1.5 in panels. Same warning as above: do **not** copy
`bench/figures/fig5_refine_quality.png` over it.

`fig7-stage-timings.png` and `fig8-mesh-reduction.png` come from
`bench/results/` (generated by `bench/generate_case_study_plots.py`, run from
the repository root) -- see the note under Layout above.

`bench/` is a separate experiment harness (see `bench/README.md`) whose every
number traces to a committed CSV in `bench/results/`; `bench/FINDINGS.md`
cross-references those CSVs against this paper's text. If you touch
refinement or component-filtering code, regenerate the underlying CSV and
figures before re-deriving `fig9-refine-scaling.png`:

```bash
uv run python -m bench.plots                    # from the repository root; CPU-only, ~seconds
cd paper && python trim-refine-scaling-figure.py
python trim-refine-quality-figure.py
python ../bench/generate_case_study_plots.py    # only if the case study itself was re-run
cp ../bench/results/fig7-stage-timings.png ../bench/results/fig8-mesh-reduction.png figures/
```

If the underlying measurements changed (not just styling), re-derive the
specific numbers quoted in prose from `bench/results/*.csv` or
`bench/FINDINGS.md` and update `paper.tex` by hand -- nothing auto-syncs the
inline numbers in Sections V and VI to the CSVs.

`fig10-fragment-removal.png` and `fig11-rigging-quality.png` remain in
`figures/` (still copyable from `bench/figures/fig8_fragment_removal.png` and
`fig_a8_rigging.png` respectively) but are not referenced by `paper.tex`:
fragment removal was cut because Table III already reports the same
convergence result, and the rigging prototype is described in Future Work
without a dedicated figure.
